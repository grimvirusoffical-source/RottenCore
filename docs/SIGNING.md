# Red-XAI signing in RottenCore (milestone 1)

Red-XAI apps are signed with **our own certificates**, not Apple's. ra-core (https://api.rottenapplestore.org)
is the certificate authority: it issues developer certificates to Red-XAI Accounts developer accounts
(Josh's lifetime Mega developer account first). RottenCore and the Poison Apple launcher verify them.
Full plan: `specs/rottencore-poisonapple-plan.md` in the Red-XAI workspace.

## Certificates
Wire-compatible with the store's `rarxai.Cert` (canonical JSON, domain `RARXAI-CERT-v1\0`): leaf kind
`developer`, up to two `ca` intermediates, top signed by a pinned Red-XAI CA root (`core.PinnedCARoots`,
**empty until the production root ceremony**, so a TEST root is used meanwhile). Cert **v2** adds an `alg`
field: `ed25519` (v1, byte-identical to rarxai) or **`p384`** (ECDSA/SHA-384, 97-byte uncompressed point,
96-byte raw `r||s`, CryptoKit-compatible). A new leaf kind **`update-signer`** certifies Red-XAI Host update
keys. Test certificates (`test: true`) and test roots are refused in production.
`core/testdata/rarxai_vector.json` is generated by the store's own code with seeded test keys and checked by
`TestRarxaiCompatVector`; P-384 chains and signatures have their own tests.

## File signatures
A **detached `<file>.rasig`** sidecar (or a GitHub release asset). A signature is *not* embedded inside the
file it signs: an embedded signature cannot cover the bytes of the container that holds it (that needs a tree
hash — future work), so Rotten Core writes a sidecar and regenerates `SHA256SUMS`.

```json
{ "alg": "ed25519|p384", "doc": "<base64 canonical FileSigDoc>", "sig": "<base64>", "chain": [ <developer cert>, <ca cert>... ] }
```
`FileSigDoc = { v, appId, version, artifact: { name, kind, sha256, bytes }, signedMs }`, signed by the
developer key under `ROTTENCORE-FILESIG-v1\0`. A file is **valid** when the chain verifies, the signature
verifies under the leaf, the sha256 and size equal the bytes on disk, and nothing is revoked.

## Revocation
ra-core's signed status ticket (`GET /v1/status`, store key, `RARXAI-STATUS-v1\0`, 6 h life) lists revoked
certificate fingerprints (any certificate in the chain), builds (`sha256:<file hash>`) and apps.

| list state | result |
|---|---|
| fresh (not expired) | valid / revoked |
| grace (expired < 7 days, offline) | valid (UI says "offline") / revoked |
| stale or none | **unverifiable**, never valid; revocations on a stale list still apply |

The last good ticket is cached at `~/Library/Application Support/RottenCore/status-ticket.json` (0600) and
only replaced by a newer valid one, so a replayed old ticket cannot un-revoke anything. The production **store public key is pinned** in `core.PinnedStoreKeys` (`core.StoreKeyHex`); it is public,
so pinning it is safe and lets revocation tickets verify.

## CLI
```
rottencore verify-signature <file> [<sig file>]   # exit 0 valid, 3 not trusted, 4 revoked
rottencore verify-update-manifest <manifest.json> <manifest.sig|ed25519:...> <keys.json> [--kid K] [--last-seq N]
rottencore fetch <https url> <dest> [--progress json]   # NDJSON progress for the loading screen
rottencore sign <file> --key dev.key.json --bundle dev.bundle.json --app <id> --app-version <v> [--platform P]
rottencore build <request.json> --key dev.key.json --bundle dev.bundle.json [--out DIR]
```
